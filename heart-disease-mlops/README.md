## Dataset and objective

The UCI Cleveland Heart Disease dataset contains 303 records and 13 input features. The original `num` target is converted into a binary `target`: zero means disease absent, and values greater than zero mean disease present. The original target is excluded from model inputs.

The data contains 164 absent and 139 present cases, four missing values in `ca`, two in `thal`, and no duplicate rows. The raw data is retained unchanged. A stratified split with `random_state=42` creates 242 training records and 61 held-out test records.

This is an educational demonstration; the results do not establish suitability for clinical use.

## Architecture
GitHub Actions automates validation and training. Docker and Kubernetes deployment are performed separately. Preprocessing is fitted within each training fold, and the deployed artifact includes both fitted preprocessing and the classifier.

### Preprocessing and model choices

- Continuous features `age`, `trestbps`, `chol`, `thalach` and `oldpeak`: median imputation and standard scaling.
- Categorical features `sex`, `cp`, `fbs`, `restecg`, `exang`, `slope`, `ca` and `thal`: most-frequent imputation and one-hot encoding with unknown categories ignored.
- Logistic Regression and Random Forest: five-fold stratified cross-validation with shuffle and seed 42.
- Hyperparameter search: eight Logistic Regression and eighteen Random Forest configurations, selected by mean CV ROC-AUC.

The processed CSVs contain the split features and binary labels. Missing values are intentionally handled inside the fitted pipeline, avoiding leakage from fitting imputation before splitting.

### Recorded results

| Model | Baseline CV ROC-AUC | Tuned CV ROC-AUC |
|---|---:|---:|
| Logistic Regression | 0.9025 | 0.9028 |
| Random Forest | 0.8927 | 0.9040 |

Random Forest was selected by the predefined CV ROC-AUC criterion. Its advantage is small, approximately 0.0013, and does not demonstrate clear superiority across all metrics. The held-out test set was not used for selection.

The selected model has 200 trees, `max_depth=5`, `min_samples_leaf=3`, `class_weight="balanced"` and `random_state=42`.

| Held-out test metric | Value |
|---|---:|
| Accuracy | 0.8852 |
| Precision | 0.8387 |
| Recall | 0.9286 |
| ROC-AUC | 0.9556 |

Test confusion matrix: 26 true positives, 28 true negatives, five false positives and two false negatives. These are the recorded demonstration results, not a guaranteed clinical performance level.

## Automated tests and CI

```bash
python -m pytest tests
python -m ruff check scripts tests --select E4,E7,E9,F
```

Five tests check preprocessing behavior, valid predictions and probabilities, and persistence across model reload. They use synthetic data rather than requiring an existing trained artifact.

The **Heart Disease CI** workflow runs on relevant pushes and pull requests to `main`, or manually through [GitHub Actions](https://github.com/kisangithub12/MLOps/actions). It installs dependencies, runs lint and tests, downloads and prepares data, trains and tunes models, evaluates and verifies the pipeline, and uploads reports and models.

Code or test errors fail the job and stop subsequent normal steps. Available artifacts are uploaded with `if: always()` to assist investigation. Logs are available within each job step. The supplied manually triggered run succeeded in **1 minute 46 seconds** and produced one artifact bundle. This workflow does not automatically deploy Docker or Kubernetes.

Ensure the final pipeline exists, then run from the project root:

```bash
docker build -t heart-disease-api:1.1 .
docker run -d --name heart-disease-api \
  -p 127.0.0.1:8001:8000 heart-disease-api:1.1
docker ps --filter name=heart-disease-api

```

Open [container Swagger](http://127.0.0.1:8001/docs) and submit a request to `/predict`. If the container name already exists, start the existing container with `docker start heart-disease-api`, or use a different name and unused host port for another container.

Example request from a second terminal:

```bash
curl --fail -X POST http://127.0.0.1:8001/predict \
  -H 'Content-Type: application/json' \
  -d '{"age":63,"sex":1,"cp":1,"trestbps":145,"chol":233,"fbs":1,"restecg":2,"thalach":150,"exang":0,"oldpeak":2.3,"slope":3,"ca":0,"thal":6}'
```

The response contains `prediction`, `label`, `confidence` and `disease_probability`. Confidence is the model probability for the predicted class; disease probability is the probability for class 1. Values depend on the input and fitted model.

The image contains Python dependencies, the API and the fitted model, and runs independently of the host virtual environment. Rebuild it after changing API code or the packaged model. Inspect logs with:

```bash
docker logs heart-disease-api
```

## Kubernetes deployment in the Lab

The following path uses Minikube, as demonstrated in the Lab:

```bash
minikube start --driver=docker --cpus=2 --memory=3800
minikube image load heart-disease-api:1.1
minikube kubectl -- apply -f k8s/
minikube kubectl -- rollout status deployment/heart-disease-api --timeout=180s
minikube kubectl -- get deployments,pods,services
```

The manifest must reference `heart-disease-api:1.1`. `imagePullPolicy: Never` uses the image loaded into the cluster. The Deployment has one replica, resource requests and limits, and startup/readiness/liveness probes on `/health`.

Start the LoadBalancer tunnel in a separate terminal and keep it running:

```bash
minikube tunnel
```

Then inspect the assigned address:

```bash
minikube kubectl -- get service heart-disease-api
```

Open `http://<EXTERNAL-IP>:8002/docs` in the Lab browser. The demonstrated address was `10.100.11.226`, but it is cluster-specific and must not be assumed for a new deployment.

For evaluator testing without a LoadBalancer tunnel, use port forwarding in another terminal:

```bash
minikube kubectl -- port-forward service/heart-disease-api 8002:8002
```

Keep that terminal open and visit [Kubernetes Swagger](http://127.0.0.1:8002/docs). The Service maps port 8002 to container port 8000.

The original local Docker Desktop path uses:

```bash
kubectl --context docker-desktop apply -f k8s/
kubectl --context docker-desktop rollout status deployment/heart-disease-api --timeout=180s
kubectl --context docker-desktop get deployments,pods,services
```

Make the specified image available to the Docker Desktop cluster before applying the manifests.

## API logging and monitoring

Request logs record HTTP method, path, status and duration without patient payloads. Prometheus scrapes `/metrics` every 15 seconds; Grafana displays availability, prediction counts, errors and response duration.

### Prometheus in the Linux Lab

Keep the Minikube tunnel running. Obtain the current Service address and generate the Lab configuration from the original Docker Desktop configuration:

```bash
API_SERVICE_IP=$(minikube kubectl -- get service heart-disease-api -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
test -n "$API_SERVICE_IP" && sed "s/host\\.docker\\.internal:8002/$API_SERVICE_IP:8002/" \
  monitoring/prometheus.yml > monitoring/prometheus-lab.yml
```

Check the generated target before starting Prometheus. These container commands use Linux host networking to reach the Lab tunnel route:

```bash
docker run -d --name heart-disease-prometheus --network host \
  -v "$PWD/monitoring/prometheus-lab.yml:/etc/prometheus/prometheus.yml:ro" \
  -v heart-disease-prometheus-data:/prometheus \
  prom/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/prometheus \
  --web.listen-address=127.0.0.1:9090
```

Open [Prometheus targets](http://127.0.0.1:9090/targets) and confirm `heart-disease-api` is **UP**. This command assumes the original configuration contains `host.docker.internal:8002`; otherwise edit its target to the current Service address explicitly.

### Grafana in the Linux Lab

```bash
docker run -d --name heart-disease-grafana --network host \
  -e GF_SERVER_HTTP_ADDR=127.0.0.1 \
  -v heart-disease-grafana-data:/var/lib/grafana \
  grafana/grafana
```

Open [Grafana](http://127.0.0.1:3000), complete its first-login setup, add a Prometheus data source with URL `http://127.0.0.1:9090`, and import `monitoring/grafana-dashboard.json`. Select the new Prometheus data source in imported panels if the saved data source identifier belongs to another instance.

These monitoring image tags follow the upstream defaults used during the demonstration. Record the resolved versions or pin tags/digests if exact monitoring-stack reproduction is required.

| Dashboard measurement | Interpretation |
|---|---|
| Availability | `up{job="heart-disease-api"}`; 1 means the latest scrape succeeded |
| Prediction requests | Requests to `/predict` since API process start |
| Prediction errors | `/predict` responses with HTTP 4xx or 5xx status |
| Average response time | Five-minute rate of duration sum divided by duration count, converted to milliseconds |

Generate a few predictions to produce recent activity. Counters reset when the API process restarts. Average duration can show no data without sufficient recent requests. Monitoring covers service behavior, not model drift or ongoing predictive accuracy.

## Lab restart and common issues

- **New terminal:** change to the project folder and activate `.venv`.
- **New VM:** source and evidence in the persistent workspace can remain, but Python environments, Docker images and the Minikube cluster may need restoration. D
- **Missing model:** rerun download, preparation and training/tuning before serving or building Docker.
- **Port already in use:** inspect the listener or select another unused host port.
- **Kubernetes image unavailable:** load the exact image tag into Minikube and confirm it matches the manifest.
- **Prometheus target down:** check the current Service IP, `/metrics` reachability and that the tunnel is still running.
- **Grafana panel errors:** select the Prometheus data source created in the current Grafana instance.

The project demonstrates repeatable training and deployment with operational monitoring. It does not include automatic production deployment, clinical validation, drift detection or a permanent public endpoint.
